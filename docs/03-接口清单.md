## 一、通用约定

| 项目 | 约定 |
| --- | --- |
| 统一前缀 | `/api`，所有接口都带 |
| 返回格式 | `{ "code": 200, "msg": "ok", "data": ... }`，所有接口都一样 |
| 成功判断 | `code === 200` |
| 请求体格式 | JSON，请求头 `Content-Type: application/json` |
| 日期格式 | `yyyy-MM-dd HH:mm:ss`，例如 `2024-05-20 12:15:00` |
| 金额 | 数字，保留两位小数，例如 `22.00` |
| 登录验证 | 有登录接口，但**不用 JWT**：登录只查一次 user 表，不返回 token；当前用户 id 由前端存在 localStorage 里，之后随请求传过来 |
| 路径参数 | 写在路径里的 `{id}`，例如 `DELETE /api/address/5` |
| 查询参数 | 拼在地址后面的 `?key=value`，例如 `GET /api/address/list?userId=1` |

路径参数和查询参数的区别，看这两个例子就明白了：

```
DELETE /api/address/5?userId=1
       └──── 路径参数 id=5 ────┘└ 查询参数 userId=1 ┘
```

返回：`data` 是一个用户对象（字段见 2.0）。按 username + password 查不到时返回 `code = 500`，`msg` 为"用户名或密码错误"，前端会把 msg 弹出来给用户看。

**关于 token**：这个接口**不需要返回 token**，也不发 JWT。前端拿到用户对象后存在 localStorage 里，之后调其它接口时把里面的 `id` 当 userId 传过来。前端登录页已经写好了（`/login`），页面上还放了三个演示账号，点一下自动填。

### 7.1 POST /api/order/create

| --- | --- | --- | --- |

| shopId | Long | 视情况 | 外卖/小卖部必填，代取快递不传 |
| stationId | Long | 视情况 | 代取快递必填，其它不传 |
| receiverName | String | 是 | 收货人姓名 |
| receiverPhone | String | 是 | 收货人手机号 |
| receiverBuilding | String | 是 | 收货宿舍楼 |
| receiverRoom | String | 是 | 收货房间号 |
| pickupCode | String | 否 | 取件码，代取快递建议填 |
| expressCompany | String | 否 | 快递公司 |
| packageSize | Integer | 否 | 1 小件，2 中件，3 大件 |
| packageWeight | BigDecimal | 否 | 包裹重量 |
| deliveryFee | BigDecimal | 否 | 配送费，不传后端按店铺的配送费算 |
| tip | BigDecimal | 否 | 小费，不传按 0 算 |
| remark | String | 否 | 备注 |
| expectTime | String | 否 | 期望送达时间 |
| items | Array | 视情况 | 商品明细数组，外卖/小卖部必填，代取快递不传 |

items 里每个元素的字段：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| goodsId | Long | 是 | 商品 ID |
| quantity | Integer | 是 | 数量 |

外卖订单请求体示例：

```json
{
  "userId": 1,
  "orderType": 2,
  "shopId": 1,
  "receiverName": "张小明",
  "receiverPhone": "13800000001",
  "receiverBuilding": "3号楼",
  "receiverRoom": "305",
  "deliveryFee": 2.00,
  "tip": 0.00,
  "remark": "拉面多加辣",
  "expectTime": "2024-05-20 12:40:00",
  "items": [
    { "goodsId": 1, "quantity": 1 },
    { "goodsId": 3, "quantity": 2 }
  ]
}
```

代取快递请求体示例（没有 items，多了驿站相关字段）：

```json
{
  "userId": 1,
  "orderType": 1,
  "stationId": 1,
  "receiverName": "张小明",
  "receiverPhone": "13800000001",
  "receiverBuilding": "3号楼",
  "receiverRoom": "305",
  "pickupCode": "8-2-3051",
  "expressCompany": "中通快递",
  "packageSize": 2,
  "packageWeight": 2.50,
  "deliveryFee": 2.00,
  "tip": 1.00,
  "remark": "有点重，麻烦送到宿舍门口"
}
```

返回：`data` 是新建的订单对象（带 id、orderNo、totalAmount）。

**后端要做的事，按顺序：**

1. 生成 `orderNo`。前端不传这个字段。建议格式 `CE + yyyyMMdd + 4 位序号`，例如 `CE202405200005`。
2. 如果是外卖/小卖部（orderType 是 2 或 3）：根据 items 里的 goodsId 查商品，取出 `goodsName`、`image`、`price`，算出每条明细的 `amount = price × quantity`，累加得到 `goodsAmount`。同时检查库存够不够，不够就返回 `code = 500`、`msg = "商品库存不足"`。
3. 如果是代取快递（orderType = 1）：`goodsAmount` 记 0。
4. 计算 `totalAmount = goodsAmount + deliveryFee + tip`。**这个值由后端算，不要信前端传的金额。**
5. 插入 `orders`，`status` 设为 1（待接单），`payStatus` 设为 1（示例项目直接当已支付），`payTime` 设为当前时间。
6. 插入 `order_item`，每条明细一行，存的是下单那一刻的名称、图片、单价（快照）。
7. 插入 `order_status_log` 一条：status = 1，operatorId = userId，operatorRole = 1，remark = "用户下单"。
8. 第 5、6、7 步要放在同一个事务里，Service 实现类的方法上加 `@Transactional`。

## 十、联调建议

1. 后端写好后，先用浏览器直接打开接口地址验证，比如 `http://localhost:8080/api/shop/list`，能看到 JSON 就说明通了。
2. 全部用演示数据里的 id 试：`userId=1`（张小明，顾客）、`riderId=1`（李大力，骑手）、`shopId=1`（兰州拉面）、`goodsId=1`（兰州牛肉拉面）、`stationId=1`（菜鸟驿站3号楼店）。
3. 前端把 `.env.development` 里 `VITE_USE_MOCK` 改成 `false`（`vite.config.ts` 的代理已经配好，不用动），重启 `npm run dev`。
4. 有一个接口调不通时，先看浏览器 F12 的 Network 面板：状态码 404 是路径写错，500 是后端报错（去 IDEA 控制台看堆栈），CORS 是跨域配置没生效。
5. 三张表串起来的流程（下单）最容易出错，建议专门测一遍：调 7.1 下单，然后去数据库看 `orders`、`order_item`、`order_status_log` 三张表是不是都多了数据，金额是不是对得上。

## 十一、补充说明（联调前看一遍）

前面十节的接口已经和前端 `src/api/` 里的代码逐条核对过，路径和参数都一致，可以照抄。这一节只讲清单里没写全、但联调时一定会遇到的事。

### 11.1 公告接口（前面没列，前端首页在用）

`GET /api/announcement/list?type=`：返回 announcement 表的数据，只返回 `status = 1` 的记录，按 `sort` 升序。

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| type | Integer | 否 | 1 只返回公告，2 只返回轮播图，不传返回全部 |

请求示例：`GET /api/announcement/list?type=1`。前端首页目前只请求 `type=1`，传 2 的那个留给首页以后做轮播图用。

### 11.2 参数放在哪里的规律

前端只有 **GET** 请求把参数拼在地址后面（查询参数），**POST / PUT** 一律放在请求体里。清单里写着“请求体参数”的，后端就用 `@RequestBody` 接；写着“查询参数”的，用 `@RequestParam` 接。

有一个例外要说清楚：`DELETE /api/cart/clear?userId=1` 的 userId 是查询参数，不是请求体，因为前端封装的 `http.delete(url, params)` 就是按查询参数发的。

### 11.3 订单状态流水怎么记

前端调 `POST /api/order/{id}/status` 时不带操作人信息，后端如果还想把 `order_status_log` 记全，有两个简单办法：

- 干脆不记 operatorId、operatorRole，这两个字段在表里允许为空，不影响运行。
- 或者按业务猜一个：顾客确认收货记 operatorRole = 1，骑手标记送达记 2，管理员操作记 3。

两种都能跑通，选一种写死就行，别在联调时纠结。

### 11.4 下单接口的两个细节

前端 `OrderCreateForm` 里有几个字段需要后端注意：

| 字段 | 情况 | 后端怎么办 |
| --- | --- | --- |
| addressId | 前端会传，但 orders 表里没有这个字段 | 忽略它，别往实体类里加，加了会报 `Unknown column` |
| expectTime | 类型是必填的字符串，用户没选时间时发过来是空字符串 `""` | 空字符串直接存 DATETIME 会报错，要么在 Service 里判断 `""` 就存 null，要么让前端传 null |
| packageSize | 代取快递以外的订单，前端可能发 0 | 0 不是有效值（有效值是 1/2/3），存之前把 0 处理成 null |
| deliveryFee | 前端会传，注释里也写了"后端应该自己再算一遍" | 后端按店铺的配送费重算，不要直接信前端传的金额 |
| items | 数组，元素是 `{ goodsId, quantity }` | 和 7.1 的说明一致，据此算 goodsAmount 并写 order_item |

### 11.5 前端项目的两个开关（前端同学看这里）

| 文件 | 现在的状态 | 什么时候要改 |
| --- | --- | --- |
| `vite.config.ts` | `/api` 转发到 `http://localhost:8080` 的代理已经配好，前端端口 5173 | 不用改 |
| `.env.development` | `VITE_USE_MOCK=true`，页面用 `src/api/mock.ts` 里的假数据 | 要连后端时改成 `false`，改完重启 `npm run dev` |

假数据开着的时候页面也能点、能下单，只是数据不会进数据库。联调时记得关掉。

另外前端响应拦截器（`src/api/request.ts`）已经把 `data` 拆出来了，页面里拿到的直接是业务数据。它判断成功的依据就是 `code === 200`，所以后端返回的 `code` 字段**必须写**，值必须是数字 200，不要写成字符串 `"200"`。
